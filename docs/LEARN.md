# Μάθε το app σου — οδηγός για τον Δημήτρη

Αυτός ο οδηγός εξηγεί τι είναι frontend, backend, security, UX και UI **χρησιμοποιώντας το ίδιο το PORTAL** ως παράδειγμα. Κάθε έννοια δείχνει σε πραγματικά αρχεία του repo, για να τα ανοίγεις και να τα βλέπεις.

---

## 1. Η μεγάλη εικόνα: τι συμβαίνει όταν κάποιος αγοράζει εισιτήριο

```
 Ο χρήστης πατάει "Αγορά" στο κινητό          ← FRONTEND (apps/mobile)
        │
        ▼
 Το app στέλνει αίτημα στον server            ← ΔΙΚΤΥΟ (HTTPS)
        │
        ▼
 Ο server ελέγχει: υπάρχουν εισιτήρια;        ← BACKEND (packages/db + Edge Functions)
 Κλειδώνει τη γραμμή, μετράει, χρεώνει
        │
        ▼
 Η Stripe παίρνει τα λεφτά                    ← ΠΛΗΡΩΜΕΣ (εξωτερική υπηρεσία)
        │
        ▼
 Ο server εκδίδει το εισιτήριο στη βάση       ← ΒΑΣΗ ΔΕΔΟΜΕΝΩΝ (Postgres/Supabase)
        │
        ▼
 Το app δείχνει το QR                         ← ξανά FRONTEND
```

Κράτα αυτό το σχήμα στο μυαλό σου. Ό,τι ακολουθεί είναι ανάλυση των κομματιών του.

---

## 2. Frontend — αυτό που βλέπει ο χρήστης

**Τι είναι:** Ο κώδικας που τρέχει **στη συσκευή του χρήστη** (κινητό ή browser). Ζωγραφίζει οθόνες, ακούει αγγίγματα, ζητάει δεδομένα από τον server.

**Στο PORTAL:**
- `apps/mobile/` — το consumer app (React Native μέσω Expo). Γράφεις TypeScript και βγαίνει πραγματικό iOS + Android app.
- `apps/venues/` — το dashboard των μαγαζιών (Next.js, τρέχει σε browser).

**Βασικές έννοιες:**
- **Component:** ένα κομμάτι οθόνης που επαναχρησιμοποιείς. Π.χ. `apps/mobile/components/EventCard.tsx` — η κάρτα του event εμφανίζεται στο feed 6 φορές, αλλά ο κώδικάς της γράφτηκε μία.
- **State:** ό,τι θυμάται η οθόνη τώρα (ποια πόλη διάλεξες, πόσα εισιτήρια θες). Όταν αλλάζει το state, η οθόνη ξαναζωγραφίζεται μόνη της — αυτό είναι όλο το React σε μία πρόταση.
- **Routing:** ποια οθόνη βλέπεις. Στο `apps/mobile/app/` κάθε αρχείο = μία οθόνη. Το `event/[slug].tsx` σημαίνει «οθόνη με παράμετρο», π.χ. `/event/ritual-013`.

**Χρυσός κανόνας:** το frontend **δεν εμπιστεύεται ποτέ τον εαυτό του**. Δείχνει τιμές και μετρητές, αλλά την αλήθεια (πόσα εισιτήρια έμειναν, πόσο κοστίζει) την ξέρει μόνο ο server. Οποιοσδήποτε μπορεί να πειράξει το app στη συσκευή του.

## 3. Backend — αυτό που δεν βλέπει κανείς

**Τι είναι:** Ο κώδικας και τα δεδομένα που τρέχουν **σε server**, μακριά από τα χέρια του χρήστη. Εκεί ζουν οι κανόνες και η αλήθεια.

**Στο PORTAL (όλα μέσω Supabase):**
- **Βάση δεδομένων (Postgres):** πίνακες σαν λογιστικά φύλλα με αυστηρούς κανόνες. Δες `packages/db/supabase/migrations/20260703100000_init_schema.sql` — εκεί ορίζεται ότι υπάρχει πίνακας `tickets`, ότι κάθε εισιτήριο ανήκει σε έναν χρήστη, ότι η guestlist είναι πάντα δωρεάν (η βάση **αρνείται** να σώσει guestlist με τιμή — αυτό λέγεται constraint).
- **Migrations:** η ιστορία της βάσης σε αρχεία. Κάθε αλλαγή στο σχήμα = νέο αρχείο SQL. Έτσι η βάση σου χτίζεται ξανά πανομοιότυπη οπουδήποτε.
- **Edge Functions:** μικρά προγράμματα στον server που κάνουν ό,τι ΔΕΝ επιτρέπεται να κάνει το app: χρεώνουν κάρτες, εκδίδουν εισιτήρια, επικυρώνουν QR. Δες `packages/db/supabase/functions/`.

**Γιατί ο μετρητής εισιτηρίων ζει στη βάση:** αν δύο άτομα αγοράσουν το τελευταίο εισιτήριο **το ίδιο δευτερόλεπτο**, κάποιος πρέπει να μπει σε σειρά. Η συνάρτηση `claim_product_quota` (στο `20260703100100_functions.sql`) **κλειδώνει τη γραμμή** του προϊόντος: ο δεύτερος περιμένει τον πρώτο, και αν τελείωσαν, παίρνει άρνηση. Αυτό στο frontend είναι αδύνατο να γίνει σωστά.

## 4. Security — οι κλειδαριές

Τρία στρώματα, από έξω προς τα μέσα:

**α) Authentication («ποιος είσαι;»)** — login. Το Supabase Auth δίνει στον χρήστη ένα **token** (ψηφιακή ταυτότητα) που το app στέλνει με κάθε αίτημα. Εμείς χρησιμοποιούμε κωδικό μιας χρήσης στο email (OTP) — χωρίς passwords, τίποτα να κλαπεί.

**β) Authorization («τι δικαιούσαι;») — RLS.** Το πιο σημαντικό αρχείο ασφαλείας του project: `packages/db/supabase/migrations/20260703100200_rls.sql`. Row Level Security σημαίνει ότι **η ίδια η βάση** φιλτράρει κάθε ερώτημα:
- Εσύ βλέπεις ΜΟΝΟ τα δικά σου εισιτήρια — ακόμα κι αν κάποιος χακέψει το app και ζητήσει «όλα τα εισιτήρια», η βάση επιστρέφει μόνο τα δικά του.
- Ένα μαγαζί δεν βλέπει ΠΟΤΕ τις πωλήσεις άλλου μαγαζιού.
- Κανένα app δεν μπορεί να γράψει στους πίνακες `orders`/`tickets` — μόνο ο server.

Γιατί στη βάση κι όχι στο app; Γιατί το app παρακάμπτεται· η βάση όχι.

**γ) Μυστικά.** Κλειδιά Stripe, service keys — μπαίνουν σε `.env` αρχεία που ΔΕΝ ανεβαίνουν στο git (δες `.gitignore`). Στο repo υπάρχουν μόνο `.env.example` χωρίς πραγματικές τιμές. **Ποτέ μην κάνεις commit κλειδί.** Αν γίνει, το θεωρείς καμένο και βγάζεις καινούργιο.

**Και το QR:** ένα screenshot εισιτηρίου δεν δουλεύει, γιατί το QR αλλάζει κάθε 60" (υπολογίζεται από μυστικό + ρολόι, όπως τα codes της τράπεζας), κι ο σαρωτής της πόρτας το επαληθεύει στον server.

## 5. UX — πώς ΝΙΩΘΕΙ το app (User Experience)

UX δεν είναι ομορφιά· είναι **πόσο εύκολα πετυχαίνει ο χρήστης αυτό που ήρθε να κάνει**. Αποφάσεις UX στο PORTAL:

- **Δύο taps από προϊόν σε πληρωμή** (spec §5). Κάθε έξτρα βήμα = χαμένες πωλήσεις. Γι' αυτό το checkout είναι bottom sheet πάνω στη σελίδα, όχι νέα οθόνη.
- **Η τιμή που βλέπεις = η τιμή που πληρώνεις.** Τα κρυφά «+ έξοδα» στο τέλος είναι ο #1 λόγος εγκατάλειψης καλαθιού — και dark pattern. Εμείς το απαγορεύουμε ΚΑΙ στη βάση (`fee_cents <= price_cents`, μέσα στην τιμή).
- **Πραγματικός μετρητής «έμειναν X».** Το ψεύτικο urgency διώχνει τον κόσμο μακροπρόθεσμα. Ο δικός μας μετρητής διαβάζει το αληθινό `quota - sold_count`.
- **Καταστάσεις οθόνης:** κάθε οθόνη σχεδιάζεται 4 φορές — φορτώνει / έχει δεδομένα / είναι άδεια / χτύπησε σφάλμα. Οι αρχάριοι φτιάχνουν μόνο τη 2η και το app «κολλάει» στις άλλες τρεις.
- **Δίγλωσσο από την πρώτη μέρα:** κάθε κείμενο περνάει από το `packages/shared/src/i18n/` — ποτέ σκληρογραμμένο string μέσα σε οθόνη. Ο τουρίστας στη Νάπα βλέπει αγγλικά αυτόματα.

## 6. UI — πώς ΦΑΙΝΕΤΑΙ το app (User Interface)

UI είναι η οπτική γλώσσα: χρώματα, γράμματα, αποστάσεις. Ο κανόνας των επαγγελματιών: **λίγες επιλογές, εφαρμοσμένες παντού** — αυτό λέγεται design system.

Το δικό μας είναι κλειδωμένο στο spec §5 και ζει σε ΕΝΑ αρχείο: `packages/shared/src/theme.ts`.
- Παλέτα: σκούρο μπλε φόντο (abyss/deep/card), χάλκινο για δράση (copper), seaglass για επιτυχία, bone για κείμενο, dim για δευτερεύον. Θες αλλαγή χρώματος; Την κάνεις σε ένα σημείο και αλλάζει παντού.
- Γραμματοσειρές: Archivo για τίτλους/UI, Space Mono για τιμές, ώρες, κωδικούς (monospace = τα ψηφία ευθυγραμμίζονται).
- Υπογραφή brand: η **αψίδα** (portal arch) στις φωτογραφίες και το «portal ring» γύρω από το QR. Κάθε γνωστό app έχει ένα τέτοιο αναγνωρίσιμο στοιχείο.

**Tailwind/NativeWind:** αντί για ξεχωριστά αρχεία CSS, γράφεις κλάσεις πάνω στο στοιχείο: `className="bg-card p-4 rounded-2xl"` = φόντο κάρτας, εσωτερικό περιθώριο, στρογγυλεμένες γωνίες. Τα ονόματα `bg-card`, `text-copper` έρχονται από το theme.ts.

## 7. Λεξιλόγιο που θα συναντάς συνέχεια

| Όρος | Στα απλά ελληνικά |
|---|---|
| API | Το «μενού» με το οποίο το app παραγγέλνει δεδομένα από τον server |
| JSON | Η μορφή που ταξιδεύουν τα δεδομένα: `{"name": "RITUAL 013"}` |
| Token / JWT | Ψηφιακή ταυτότητα με υπογραφή — αποδεικνύει ποιος είσαι χωρίς password σε κάθε αίτημα |
| Webhook | Η Stripe «χτυπάει το κουδούνι» του server μας όταν ολοκληρωθεί μια πληρωμή |
| Migration | Αρχείο SQL που αλλάζει το σχήμα της βάσης — η βάση έχει version control όπως ο κώδικας |
| RLS | Κανόνες μέσα στη βάση: ποια ΓΡΑΜΜΗ πίνακα βλέπει ο καθένας |
| Environment variable (.env) | Μυστικά και ρυθμίσεις έξω από τον κώδικα |
| TypeScript | JavaScript με «τύπους» — ο υπολογιστής σε προειδοποιεί για λάθη πριν τρέξει το app |
| Monorepo | Ένα repo, πολλά πακέτα (`apps/`, `packages/`) που μοιράζονται κώδικα |
| Edge Function | Μικρό πρόγραμμα server χωρίς να συντηρείς server |

## 8. Πώς να διαβάζεις αυτό το repo

1. `PORTAL-SPEC.md` — το σύνταγμα. Τι χτίζουμε και γιατί.
2. `packages/db/supabase/migrations/` — με τη σειρά: schema → functions → rls. Αν καταλάβεις αυτά τα 3 αρχεία, καταλαβαίνεις το 70% του συστήματος.
3. `apps/mobile/app/(tabs)/index.tsx` — η πρώτη οθόνη. Δες πώς ζητάει events και τα δείχνει.
4. `packages/db/supabase/functions/create-payment-intent/` — η καρδιά των χρημάτων. Διάβασέ το με το σχήμα του κεφαλαίου 1 δίπλα.

**Συμβουλή:** μην προσπαθήσεις να τα μάθεις όλα πριν προχωρήσεις. Χτίζουμε, βλέπεις τι κάνει κάθε κομμάτι, ρωτάς «γιατί έγινε έτσι;» — έτσι μαθαίνεται αυτή η δουλειά.
